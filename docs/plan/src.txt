War Thunder Tactical Command

V10 项目实施计划｜双地图战术标绘系统
版本： 1.0（基于 UI V10 冻结需求）
日期： 2026-10-10
状态： 可进入技术验证；8111 实际采样能力和双图输出行为尚需实测
部署目标： 一台香港 VPS + 轻量 Windows Agent + 手机 / PC 响应式网页
适用场景： 《战争雷霆》8v8 连队战、空地混合战术协同


 一句话定义： 所有人都能打开同一张实时战术地图，在陆战、空战、双地图间切换；系统自动同步参战
 队员的位置和朝向，队员通过单地图模式直接标点、画进攻路线、框选区域、指出攻击来源。它是地图工
 具，不是战况管理后台。




0. 本版本确认的设计决策
主题       已决定的方案

页面尺寸     整页锁定浏览器可用视口；无水平、垂直滚动；适配手机竖屏、横屏、桌面

地图外观     地图视口始终 1:1 正方形，优先最大化占据顶栏以下的高度；图片等比绘制，严禁拉伸

顶栏       仅保留应用标识、陆战 / 空战 / 双图切换、指挥 / 成员 UI 切换及必要连接指示

单地图      桌面和横屏：左侧尽可能大的正方形地图 + 右侧纯标绘工具；窄屏竖屏：地图在上、紧凑工具在下

双地图      同时显示陆战图和空战图，操作栏完全消失；宽屏左右并排、窄屏上下排列；两张图分别独立缩放

功能主线     地图标点、进攻路线（折线与钢笔曲线）、区域框选、人工攻击来源方向；地图显示实时友军位置及朝向

两种 UI    指挥 / 成员只是默认布局和控件密度不同；无角色级操作权限差异，任何成员均可切换

数据上传     每名参战队员 Windows Agent 只读取本人及必要地图元信息，不要求指挥员运行游戏

双地图来     至少 1 名空战成员保持空战地图，陆战成员提供陆战地图；服务器分别缓存两种图片与坐标参数
源

后端       香港 VPS；单实例 Rust + Axum + Tokio；SQLite；WebSocket/WSS；无需 Redis / Kafka / Cloudflare DO

频率       10Hz 是端到端态势同步目标；实际 8111 新样本频率须首先测量，不能用重复轮询冒充 10Hz

本期不做     游戏内 Overlay、鼠标监听、战损报告、死亡自动标记、载具受损部位管理、编队状态栏、战后回放、自动敌情
         采集归档


范围约束： “不做复杂敌情”不意味着删掉基础敌军点标。人工敌方位置、型号简写和攻击来源箭头依旧属
于基础标绘，但不做独立情报管理后台。

1. 使用场景与关键流程

1.1 标准连队协同
1. 队员在 PC 上启动《战争雷霆》和轻量 Agent；Agent 自动读取本地 127.0.0.1:8111。
2. 至少一名飞行员使用空战地图类型、一名陆战成员使用陆战地图类型，为房间提供两套底图和坐标元数
  据。
3. 队员和指挥员在手机 / PC 浏览器中进入同一房间。浏览器可选陆战、空战或双图模式。
4. 地图显示全队本人上报的友军位置、昵称与朝向；指挥者在单图模式标注集合点、目标或进攻路径。
5. 服务器立刻向房间内所有网页同步标绘；双地图只负责观察，同一份世界坐标会被正确投影到两张图。
6. 若受到不明方向攻击，队员在单图模式用“来源”工具画出受袭点与疑似来袭方向。来源明确标识为人工
  报告 / 未确认。


1.2 手机操作原则
• 单图是编辑工作台；双图是态势总览，切换不改变用户权限。
• 触控点击地图不会误触触发工具；只有显式选择工具后才创建标绘。
• 地图双指缩放、单指平移与绘制手势要区分。绘制中允许取消、撤销上一节点、完成。
• 所有必要操作都能通过点击按钮完成，不能只能依赖右键、悬停或键盘。
• 需要选择目标点时，优先缩放地图，而不是让弹出表单占据大半屏幕。

手机竖屏： 单图 = 上方大正方形地图 + 下方按可用空间压缩的工具；双图 = 两张正方形地图上下排，整屏同

3.2 强制布局算法
令 W、H 为浏览器实际可用的工作区宽高（已扣除顶栏 T、安全区和容器间距）。令地图边长为 S：

 • 单图桌面：S = min(H - T - padding, W - sideWidth - gap - padding)。
 • 双图横排：S = min(H - T - padding, (W - gap - padding) / 2)。
 • 双图竖排：S = min(W - padding, (H - T - gap - padding) / 2)。
 • 单图竖排：先给紧凑工具区分配必要高度 toolsH，S = min(W - padding, H - T - toolsH - gap - padding)。

实现建议：height: 100dvh; overflow: hidden 与 ResizeObserver / visualViewport 自适应；地图容器始终 aspect-ratio:
1 / 1。地图背景图片以等比变换绘制，不能通过 CSS 分别拉伸宽、高。


 极端小屏存在天然的空间取舍：当两张正方形地图和顶栏无法同时达到舒适点击尺寸时，优先满足无滚动
 + 正方形，缩小标记密度、隐藏非必要文字，并提供单图切换放大。


3.3 视觉层级
 • 地图是视觉主体：浅色低饱和地形图、清晰网格、克制的灰绿 / 米灰 UI。
 • 颜色只表示含义：蓝色友军、红色人工敌情 / 疑似来源、琥珀色命令和进攻路径、青色侦察。不要把整个
   界面染成高饱和色。
 • 优先模仿战雷图标语义与玩家已熟悉的类别；图标映射从采集样本验证，未经授权不直接复制游戏图像资
   源。
 • 禁止常驻状态卡、图例大面板、列表墙、说明段落；工具栏入口固定且简短。
 • 地图边缘仅可显示必要的缩放 / 居中按钮，优先采用不遮挡标绘的角落。
 • 单图交互区在未选工具时只显示工具按钮；选择对象后出现仅与该对象有关的简短编辑控件。


3.4 指挥 / 成员 UI
两个模式共享：同一房间、同一 WebSocket 协议、同一可执行操作集、同一读写权限。

 • 指挥界面： 默认展开工具名称、图形编辑选项，适合连续绘图。
 • 成员界面： 默认折叠为图标工具 / 轻量标记入口，适合快速查看。
 • 用户随时切换，切换时视口位置、编辑历史、已绘标记保持不变。
 • 服务端不得根据“UI 模式”拦截编辑权限；只校验是否为该房间有效连接及输入是否合法。

5.2 10Hz 是“有效数据”目标
先在自定义对局分别测试每秒 2 / 5 / 10 / 20 次轮询，记录每次响应的耗时、本人坐标 / 方向变化、新样本比
率，按移动和静止状态分组。

 • Agent → Server 上报： 最多 10Hz；如果本地重复返回同一份有效状态，不必将重复包当作新数据。
 • Server → Web 广播： 最多 10Hz 聚合全队快照；标绘修改事件立即广播。
 • Web 渲染： 尝试 60FPS，低端机可降至 30FPS；对有效位置做 100–150ms 缓冲插值，过期后停止预
    测。
 • 数据质量： 每个状态带 sampledAt、seq、sampleAgeMs，一旦数据超过 500ms 显示“数据延迟”，超过 2s 停
    止实时外推（阈值可按实测调整）。

频率不可硬性从 8111 “榨”出来；如果实测仅有 5Hz 新样本，网络仍可按轻量节奏同步，页面平滑插值，
但必须显示真实性能。


5.3 双地图投影
每套底图独立携带：imageHash、width/height、map_min/max、hud_type、generation、providerId、capturedAt、
battleEpoch。

一个地图对象的归一化坐标 (x,y) 转世界坐标的候选变换：

  worldX = mapMinX + x * (mapMaxX - mapMinX)
  worldY = mapMinY + y * (mapMaxY - mapMinY)


反过来画到另一张图时，用目标图对应的范围逆变换；必须先实测两图是否共享这个坐标约定、Y 轴方向是否
一致和裁切是否准确。

 • 所有自定义标点、线路和区域只保存同一世界坐标系，避免双图重复存储和投影漂移。
 • 空战地图更大，地面标点可能变得密集；空战总览中按缩放级别隐藏次要标签，但保留图形。
 • 地图超出范围的标记不强行画到边缘；在世界范围外时直接不显示，或者使用明确的“范围外”提示。

 1. 主陆战 / 空战提供者上线时上传经过尺寸 / 格式 / 哈希校验的地图图片和信息。
 2. 新提供者只能在战局身份、HUD 类型、范围 / 图片满足校验时接管。
 3. 提供者失联时保持最后一张已确认属于当前战局的地图；友军过期状态单独处理。
 4. 房间新战局开始时创建新 battleEpoch，上一战局标绘默认归档，不直接覆盖到下一局。

         { "p": [1440, 2480], "in": [1360, 2500], "out": null }
       ]
     }
 }


攻击来源： 保存受袭点、估计方向角、可选扇区宽度；只代表成员人工判断，默认不自动创建一个“已确认
敌军”的精确点标。

消息类型                           方向                  用途

room.join / room.snapshot      双向                  加入房间后全量同步标记 / 地图元数据

annotation.applied             VPS → Web           编辑成功并广播新版本

ping / pong                    双向                  心跳与延迟监测


• 标绘命令携带 operationId 以防断线重试造成重复创建。
• 服务端验证地理坐标范围、字符串长度、最大控制点个数和消息体大小。
• 标绘 CRUD 操作按事件驱动，不混入每 100ms 的位置包。
• 用户可以用成员或指挥视图发送同样的操作消息；后端不读取 uiMode 决定权限。


6.3 SQLite 最小表

表名                          保存内容

rooms                       房间配置、访问令牌哈希、创建 / 过期时间

battles                     房间战局 epoch、地图匹配结果、开始结束时间

map_assets                  双图图片文件索引、范围、哈希、提供者、版本

10Hz 位置状态只留在内存中，本期不把每个位置样本写进 SQLite；否则徒增 IO 和历史数据复杂度。

7.1 建议资源
• 从 1–2 vCPU / 2GB RAM / 20–40GB SSD 开始，Linux，无 GPU。
• 优先香港机房，因为用户不准备办理大陆 ICP 备案；香港线路到大陆的 RTT / 抖动要用实际连队成员网络
  测试。
• 本期仅 8 个 Agent + 若干网页，性能瓶颈更可能来自 8111 有效刷新和公网 RTT，而非 CPU。
• 不购买域名也能访问公网 IP；但移动端需要 HTTPS 才能稳定使用受限 Web 能力与 PWA。采用支持 IP 地
  址证书的 ACME 服务并自动续期，部署前先做可行性验证；若证书申请 / 续期不成功，应保留可靠的
  HTTPS 备用方案，而不是直接默认长期使用明文 WS。
• 只开放必要的外部端口，例如 443；8111 永远仅由本地 Agent 读取，不得映射公网。


7.2 带宽容量（估算，不是实测）
8 位队员 × 10 次上报 / 秒 = 80 条上行位置消息 / 秒。假设 8 个浏览器、每秒 10 帧、每帧 1KB 全队快照，服
务端下行约 80KB/s，约 288MB/小时（未计 TCP / TLS / 其它请求）。地图底图按战局图片哈希缓存，避免
重复上传。


7.3 基础安全与可用性
• 房间码只是入口标识，必须另有不可预测的会话 / 设备凭证；房间之间的数据严格隔离。
• Agent 的 HTTP 目标写死 127.0.0.1:8111；仅上传白名单字段，过滤不需要的敌方地图对象。
• 限制标绘更新频率、地图文件大小、异常 JSON、恶意文本；网页对标签文本转义。
• Caddy TLS、systemd 自动重启、SQLite 每日备份、地图缓存定期清理，日志默认不记录精确个人位置
  轨迹。
• 单实例 VPS 重启后：标绘从 SQLite 恢复、实时位置等待 Agent 重新上报、网页自动重连。
• 使用边界： 现阶段只读采集自身友军信息、人工报告敌军和方向；不做自动提取 / 汇总曾短暂出现的敌军
  目标。正式用于比赛前应核对 Gaijin 当前第三方工具和比赛规则。
