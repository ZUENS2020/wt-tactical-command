## 1. 使用场景与关键流程

### 1.1 标准连队协同

1. 队员在 PC 上启动《战争雷霆》和轻量 Agent；Agent 自动读取本地 127.0.0.1:8111。
2. 至少一名飞行员使用空战地图类型、一名陆战成员使用陆战地图类型，为房间提供两套底图和坐标元数据。
3. 队员和指挥员在手机 / PC 浏览器中进入同一房间。浏览器可选陆战、空战或双图模式。
4. 地图显示全队本人上报的友军位置、昵称与朝向；指挥者在单图模式标注集合点、目标或进攻路径。
5. 服务器立刻向房间内所有网页同步标绘；双地图只负责观察，同一份世界坐标会被正确投影到两张图。
6. 若受到不明方向攻击，队员在单图模式用“来源”工具画出受袭点与疑似来袭方向。来源明确标识为人工报告 / 未确认。

### 1.2 手机操作原则

- 单图是编辑工作台；双图是态势总览，切换不改变用户权限。
- 触控点击地图不会误触触发工具；只有显式选择工具后才创建标绘。
- 地图双指缩放、单指平移与绘制手势要区分。绘制中允许取消、撤销上一节点、完成。
- 所有必要操作都能通过点击按钮完成，不能只能依赖右键、悬停或键盘。
- 需要选择目标点时，优先缩放地图，而不是让弹出表单占据大半屏幕。

### 3.1 结构

**桌面 / 横屏单图：**


**桌面 / 横屏双图：**

```diagram
{{dual}}
```

**手机竖屏：** 单图 = 上方大正方形地图 + 下方按可用空间压缩的工具；双图 = 两张正方形地图上下排，整屏同时可见，禁止滚动。极窄 / 低矮屏幕允许缩小地图和工具文字，但不得扭曲地图。

### 3.2 强制布局算法

令 W、H 为浏览器实际可用的工作区宽高（已扣除顶栏 T、安全区和容器间距）。令地图边长为 S：

- **单图桌面：**`S = min(H - T - padding, W - sideWidth - gap - padding)`。
- **双图横排：**`S = min(H - T - padding, (W - gap - padding) / 2)`。
- **双图竖排：**`S = min(W - padding, (H - T - gap - padding) / 2)`。
- **单图竖排：**先给紧凑工具区分配必要高度 toolsH，`S = min(W - padding, H - T - toolsH - gap - padding)`。

实现建议：`height: 100dvh; overflow: hidden` 与 ResizeObserver / visualViewport 自适应；地图容器始终 `aspect-ratio: 1 / 1`。地图背景图片以等比变换绘制，不能通过 CSS 分别拉伸宽、高。

<div class="note" markdown="1">
极端小屏存在天然的空间取舍：当两张正方形地图和顶栏无法同时达到舒适点击尺寸时，优先满足无滚动 + 正方形，缩小标记密度、隐藏非必要文字，并提供单图切换放大。
</div>

### 3.3 视觉层级

- 地图是视觉主体：浅色低饱和地形图、清晰网格、克制的灰绿 / 米灰 UI。
- 颜色只表示含义：蓝色友军、红色人工敌情 / 疑似来源、琥珀色命令和进攻路径、青色侦察。不要把整个界面染成高饱和色。
- 优先模仿战雷图标语义与玩家已熟悉的类别；图标映射从采集样本验证，未经授权不直接复制游戏图像资源。
- 禁止常驻状态卡、图例大面板、列表墙、说明段落；工具栏入口固定且简短。
- 地图边缘仅可显示必要的缩放 / 居中按钮，优先采用不遮挡标绘的角落。
- 单图交互区在未选工具时只显示工具按钮；选择对象后出现仅与该对象有关的简短编辑控件。

### 3.4 指挥 / 成员 UI

两个模式共享：同一房间、同一 WebSocket 协议、同一可执行操作集、同一读写权限。

- **指挥界面：**默认展开工具名称、图形编辑选项，适合连续绘图。
- **成员界面：**默认折叠为图标工具 / 轻量标记入口，适合快速查看。
- 用户随时切换，切换时视口位置、编辑历史、已绘标记保持不变。
- 服务端不得根据“UI 模式”拦截编辑权限；只校验是否为该房间有效连接及输入是否合法。

### 3.5 标绘操作细节

| 工具 | 交互 | 数据形状 |
|---|---|---|
| 标点 | 选择类别 → 点击地图 → 可选名称 → 提交 | 世界坐标点 Point |
| 折线路线 | 逐点点击；完成 / 撤销末点 / 取消（首轮联机测试使用的路线工具） | LineString + arrowhead |
| 钢笔曲线（P5 / 下一轮） | 点击创建拐点；拖动创建平滑点；完成后支持节点 / 手柄编辑。首轮不实现 | 三次 Bézier 控制点（预留格式） |
| 区域 | 点击拖动形成矩形；移动 / 调整边界 | 世界坐标矩形 Rect |
| 攻击来源 | 第一次点击受击点，第二次点击来源方向；可改为扇形估计 | 原点 + 方位角 + 可选角宽 |
| 选择 | 点击标记，显示可编辑属性和删除按钮 | 标记 ID + 服务器版本号 |

绘制工具统一使用撤销、取消和提交动作；桌面可增加快捷键，手机也要有可点击按钮。路线建议保留“自由平移”模式，防止手机绘制时意外拉动地图。

## 5. 8111 采集与双地图同步

### 5.1 使用的本地接口

| Endpoint | 作用 | 首版使用方式 |
|---|---|---|
| `GET /map_info.json` | map_min/max、HUD 类型、generation、网格信息 | 地图坐标变换与变化检测；范围切换用于判断本人状态与战局 |
| `GET /map_obj.json` | 当前本地地图对象 | 识别本人的坐标和朝向；不把所有对象广播 |
| `GET /map.img` | 当前客户端地图图片 | 陆战 / 空战指定提供者上传地图图片 |
| `GET /state`、`GET /indicators` | 可选车辆 / 飞机状态 | 仅辅助识别与诊断，不依赖它们保证死亡识别 |
| `GET /mission.json` | 对局状态 | 辅助判断新战局与结束（BATTLE-01 的主要信号之一） |

**注意：**社区逆向文档支持以上端点存在，但官方客户端显示双地图不等于 8111 一定能同时输出两张图片。首轮按两名提供者分工实现，并实测地图切换对应的 API 行为；如果来源暂缺，继续显示最近已确认属于该战局的缓存地图。

### 5.2 10Hz 是“有效数据”目标

先在自定义对局分别测试每秒 2 / 5 / 10 / 20 次轮询，记录每次响应的耗时、本人坐标 / 方向变化、新样本比率，按移动和静止状态分组；同时录制本人图标缺失、地图范围切换等状态样本（见 5.5）。

- **Agent → Server 上报：**最多 10Hz；如果本地重复返回同一份有效状态，不必将重复包当作新数据。
- **Server → Web 广播：**最多 10Hz 聚合全队快照；标绘修改事件立即广播。
- **Web 渲染：**尝试 60FPS，低端机可降至 30FPS；对有效位置做 100–150ms 缓冲插值，过期后停止预测。
- **数据质量：**每个状态带 sampledAt、seq、sampleAgeMs，一旦数据超过 500ms 显示“数据延迟”，超过 2s 停止实时外推（阈值可按实测调整）。

频率不可硬性从 8111 “榨”出来；如果实测仅有 5Hz 新样本，网络仍可按轻量节奏同步，页面平滑插值，但必须显示真实性能。

### 5.3 双地图投影

每套底图独立携带：imageHash、width/height、map_min/max、hud_type、generation、providerId、capturedAt、battleEpoch。

一个地图对象的归一化坐标 (x,y) 转世界坐标的候选变换：

```code
worldX = mapMinX + x * (mapMaxX - mapMinX)
worldY = mapMinY + y * (mapMaxY - mapMinY)
```

反过来画到另一张图时，用目标图对应的范围逆变换；必须先实测两图是否共享这个坐标约定、Y 轴方向是否一致和裁切是否准确。

- 所有自定义标点、线路和区域只保存同一世界坐标系，避免双图重复存储和投影漂移。
- 空战地图更大，地面标点可能变得密集；空战总览中按缩放级别隐藏次要标签，但保留图形。
- 地图超出范围的标记不强行画到边缘；在世界范围外时直接不显示，或者使用明确的“范围外”提示。
- map_generation 可能是各客户端自己的变化计数，不能单靠它当作跨玩家共享战局 ID。使用房间战局 epoch + 实际地图图像 / 范围匹配，提供者之间不一致时由网页提示人工确认（详见 5.4 与 BATTLE-01）。
- 每场首次联机前，使用同一已知位置至少 3 个校准点做地空互投验证，输出投影误差。

### 5.4 数据来源切换与战局识别

1. 主陆战 / 空战提供者上线时上传经过尺寸 / 格式 / 哈希校验的地图图片和信息。
2. 新提供者只能在战局身份、HUD 类型、范围 / 图片满足校验时接管。
3. 提供者失联时保持最后一张已确认属于当前战局的地图；友军过期状态单独处理。
4. 房间新战局开始时创建新 battleEpoch，上一战局标绘默认归档，不直接覆盖到下一局。

**战局识别（BATTLE-01，独立 Issue）：**

- **自动检测：**以各 Agent 上报的 mission.json 状态转换作为新战局 / 战局结束的触发信号，再用地图图像哈希与 map_min/max 在多个提供者之间交叉匹配，确认属于同一张地图、同一场战局后才创建新 battleEpoch 并接受该底图。
- **提供者不一致：**当不同提供者的状态转换、图像哈希或范围互相矛盾（例如一人已进入新局、另一人仍在上一局）时，不自动切换；在网页弹出简短的人工确认提示（新战局 / 仍为当前战局），任何房间成员均可确认，与“无角色级权限差异”一致。
- **确认前：**继续显示上一份已确认的地图与标绘，并在顶栏提示“战局待确认”；不得把未确认地图叠加到当前战局。
- 识别规则与阈值以 P0 实测样本为准，记录到 fixtures 中做回归测试。

### 5.5 “本人”状态与缺失处理

本人图标从 `map_obj.json` 中消失、或 `map_info.json` 的地图范围发生切换时，Agent **不得静默停止上报**，而应给出明确的本人状态，由服务器转发给网页：

| 状态 | 典型场景（判定规则以 DATA-04 实测为准） | Agent 行为 | 网页显示 |
|---|---|---|---|
| `alive` | map_obj 中可识别本人图标，地图范围与当前底图一致 | 正常上报位置 / 朝向 | 蓝色实时友军图标 |
| `dead_or_spawning` | 阵亡后本人图标消失；处于重生 / 选车界面 | 上报状态 + 最后有效位置的时间戳 | 灰色最后已知位置 + 数据年龄（如“32s 前”） |
| `spectating` | 阵亡后观战，地图对象可能来自其他视角 | 上报状态；不得把观战对象误当成本人 | 同上，灰色最后已知位置 + 年龄 |
| `in_air_vehicle` | 陆战玩家临时驾驶飞机，地图切换为空战范围 | 上报状态；该时段不作为陆战地图提供者，空战范围数据需按对应范围换算后才可使用 | 按换算结果显示，无法可靠换算时灰显最后已知陆战位置 + 年龄 |
| `unknown` | 无法判定上述任一状态 | 上报 unknown，而不是不发消息 | 灰色最后已知位置 + 年龄 |

- 状态变化立即上报；没有有效位置时仍保持低频状态心跳，使服务器能区分“Agent 在线但本人缺失”和“Agent 失联”。Agent 失联（超过 2s 无消息）由服务器单独标记为过期，处理方式同 5.2。
- 本人状态只用于正确显示友军图标，**不生成死亡标记、不记录战损**，与 2.4 的排除范围一致。
- 地图范围切换同时作为地图提供者暂停 / 战局识别的输入（见 5.4），避免把空战范围图片误当作陆战底图。

## 6. 房间数据与通信协议（建议草案）

### 6.1 自定义标绘模型

```code
{
  "id": "ann-89c1",
  "roomId": "TEAM-07",
  "battleEpoch": "2026-10-10-b2",
  "kind": "point",
  "subtype": "airstrike",
  "scope": "both",
  "geometry": { "point": { "x": 1430.2, "y": 2260.1 } },
  "label": "西侧目标",
  "createdBy": "member-03",
  "updatedAt": 1791600000123,
  "version": 1
}
```

kind 可取 `point | route | region | source`；subtype 随类别决定。自定义标记的颜色和图形必须由固定映射表决定，不能把 label 或任意 HTML 作为可执行内容渲染。`version` 由服务器在每次确认编辑时递增并返回，客户端只用于显示与同步，MVP 不据此拦截编辑。

**折线路线几何结构（首轮实现）：** 记录世界坐标节点序列与终点箭头。

```code
{
  "kind": "route",
  "subtype": "attack",
  "geometry": {
    "points": [[1200, 2600], [1440, 2480], [1580, 2300]],
    "arrowhead": "end"
  }
}
```

**曲线路线几何结构（预留格式，P5 / 下一轮实现）：** 记录世界坐标锚点 p、进入控制点 in、离开控制点 out；两锚点之间使用三次 Bézier。画布缩放只是显示变换，不修改实际路线坐标。首轮协议保留该结构定义，服务端可暂不接受此类几何。

```code
{
  "kind": "route",
  "subtype": "attack",
  "geometry": {
    "segments": [
      { "p": [1200, 2600], "in": null, "out": [1280, 2560] },
      { "p": [1440, 2480], "in": [1360, 2500], "out": null }
    ]
  }
}
```

**攻击来源：** 保存受袭点、估计方向角、可选扇区宽度；只代表成员人工判断，默认不自动创建一个“已确认敌军”的精确点标。

### 6.2 WebSocket 消息建议

| 消息类型 | 方向 | 用途 |
|---|---|---|
| `room.join` / `room.snapshot` | 双向 | 加入房间后全量同步标记 / 地图元数据 |
| `agent.telemetry` | Agent → VPS | 本人 10Hz 目标采样状态，含显式本人状态（alive / dead_or_spawning / spectating / in_air_vehicle / unknown） |
| `room.telemetry` | VPS → Web | 每 100ms 合并一份当前队员状态（含本人状态与数据年龄） |
| `map.asset` / `map.changed` | Agent / VPS → Web | 两种地图资源上传与变更通知 |
| `battle.confirm` | VPS ↔ Web | 提供者不一致时请求 / 提交新战局人工确认（BATTLE-01） |
| `annotation.create` | Web → VPS | 新建标点 / 路线 / 区域 / 攻击来源 |
| `annotation.update` | Web → VPS | 编辑对象，带 id；expectedVersion 可选，MVP 不强制校验 |
| `annotation.delete` | Web → VPS | 软删除对象；支持撤销 |
| `annotation.applied` | VPS → Web | 服务器定序确认编辑并广播新版本号 |
| `ping` / `pong` | 双向 | 心跳与延迟监测 |

- 标绘命令携带 operationId 以防断线重试造成重复创建。
- **MVP 并发策略：**服务器按到达顺序为编辑定序，后写覆盖（last-write-wins），每次确认返回新版本号；不做冲突提示 UI，被覆盖的修改可通过撤销恢复。
- 服务端验证地理坐标范围、字符串长度、最大控制点个数和消息体大小。
- 标绘 CRUD 操作按事件驱动，不混入每 100ms 的位置包。
- 用户可以用成员或指挥视图发送同样的操作消息；后端不读取 uiMode 决定权限。

### 6.3 SQLite 最小表

| 表名 | 保存内容 |
|---|---|
| `rooms` | 房间配置、访问令牌哈希、创建 / 过期时间 |
| `battles` | 房间战局 epoch、地图匹配结果、开始结束时间 |
| `map_assets` | 双图图片文件索引、范围、哈希、提供者、版本 |
| `annotations` | 当前标绘几何、类型、标签、版本、创建者、软删除标志 |
| `annotation_events` | 编辑 / 删除事件与可撤销历史（适度保留） |
| `devices` | Agent 配对标识与短期令牌索引 |

10Hz 位置状态只留在内存中，本期不把每个位置样本写进 SQLite；否则徒增 IO 和历史数据复杂度。

## 7. 香港 VPS 部署方案

```diagram
{{deploy}}
```

### 7.1 建议资源

- 从 1–2 vCPU / 2GB RAM / 20–40GB SSD 开始，Linux，无 GPU。
- 优先香港机房，因为用户不准备办理大陆 ICP 备案；香港线路到大陆的 RTT / 抖动要用实际连队成员网络测试。
- 本期仅 8 个 Agent + 若干网页，性能瓶颈更可能来自 8111 有效刷新和公网 RTT，而非 CPU。
- **HTTPS 采用域名方案：**移动端需要 HTTPS 才能稳定使用受限 Web 能力与 PWA。购买一个域名（费用很小，约每年数十元人民币）并解析到香港 VPS；香港服务器使用域名无需 ICP 备案。Caddy 为该域名自动签发并续期常规 Let's Encrypt 证书。
- **不再采用 IP 地址证书：**IP 证书有效期很短，一旦续期失败会在比赛中途中断手机端 WSS；域名证书方案成熟、续期由 Caddy 自动完成。
- 只开放必要的外部端口，例如 443；8111 永远仅由本地 Agent 读取，不得映射公网。

### 7.2 带宽容量（估算，不是实测）

8 位队员 × 10 次上报 / 秒 = 80 条上行位置消息 / 秒。假设 8 个浏览器、每秒 10 帧、每帧 1KB 全队快照，服务端下行约 80KB/s，约 288MB/小时（未计 TCP / TLS / 其它请求）。地图底图按战局图片哈希缓存，避免重复上传。

### 7.3 基础安全与可用性

- 房间码只是入口标识，必须另有不可预测的会话 / 设备凭证；房间之间的数据严格隔离。
- Agent 的 HTTP 目标写死 127.0.0.1:8111；仅上传白名单字段，过滤不需要的敌方地图对象。
- 限制标绘更新频率、地图文件大小、异常 JSON、恶意文本；网页对标签文本转义。
- Caddy 自动 TLS（域名证书）、systemd 自动重启、SQLite 每日备份、地图缓存定期清理，日志默认不记录精确个人位置轨迹。
- 单实例 VPS 重启后：标绘从 SQLite 恢复、实时位置等待 Agent 重新上报、网页自动重连。
- **使用边界：**现阶段只读采集自身友军信息、人工报告敌军和方向；不做自动提取 / 汇总曾短暂出现的敌军目标。正式用于比赛前应核对 Gaijin 当前第三方工具和比赛规则。

## 9. 验收标准（Definition of Done）

### 9.1 UI

- 页面在 320×568、390×844、844×390、1280×720、1536×698、1440×900 下无网页级横纵滚动；手机浏览器地址栏不计入网页高度。
- 所有地图边长相同方向像素差 ≤1px；图片不变形；可独立缩放 / 平移。
- 电脑单图最大化占据顶栏以下可用高度，右侧只出现当前工具；双图完全没有右操作栏。
- 手机竖屏双图同时存在，横屏允许并排；单图的工具始终可达。
- 所有基础标点、进攻路线（折线）、区域与来源标注均可用触屏创建、编辑、撤销、删除；钢笔曲线不属于首个版本的验收范围。
- 切换陆战 / 空战 / 双图或指挥 / 成员 UI，不会丢失地图标记和操作权限。

### 9.2 数据与协同

- 本人位置、朝向在至少 8 台采集端可用；不会把任意 map_obj 对象误当成自己的队员。
- 本人图标缺失或地图范围切换（阵亡、重生 / 选车、观战、陆战玩家临时驾驶飞机）时，Agent 上报明确状态（alive / dead_or_spawning / spectating / in_air_vehicle / unknown），不静默；网页将该友军显示为灰色最后已知位置并标注数据年龄。
- 双图标绘投影误差可量化并在约定容差内；图像不匹配时阻止错误叠加。
- 完整单场 8 人测试中，目标10Hz 网络快照、p95 新有效数据到可见 UI 的时延目标 ≤250ms（受 8111 实际刷新与网络条件约束）。
- Agent 失联超过 2s 不再预测位置；地图提供者断线时不立即删除已校验底图。
- 每次标绘编辑均有服务器定序与版本确认；并发编辑按后写覆盖处理且可撤销；断线重连后与服务端一致；跨战局不会串标记。
- 新战局可通过 mission.json 状态转换与地图匹配自动识别；提供者不一致时网页提示人工确认，确认前不切换地图。
- 服务端不公开 8111、不记录非必要个人数据、不自动跨队员采集 / 共享敌军地图对象。

### 9.3 上线 / 回滚

- 通过域名的 HTTPS / WSS 可从至少两种手机网络访问；Caddy 证书自动签发 / 续期已验证，域名与证书到期有监控提醒。
- 单 VPS 重启可恢复房间标绘；静态资源有缓存和更新策略。
- 保存上一版稳定构建；服务器程序更新失败可以快速回滚。
- Windows Agent 附带一页图文安装说明，队员可按说明处理 SmartScreen / 杀毒软件拦截并完成首次启动。

## 10. 风险与对应策略

| 风险 | 影响 | 应对 |
|---|---|---|
| 8111 不产生 10Hz 有效坐标 | 飞机位置卡顿 | 先量测；显示真实样本率，插值和降级；不要发重复包伪装高频 |
| 飞行员选空战地图不改变 8111 底图 | 无法即时采集完整双图 | 先实测；缓存地图资产，预置已确认底图及范围；不承诺无源自动切换 |
| 地空地图世界坐标不一致 | 标注位置偏移 | 建立成对校准样本与地图元数据转换，误差超限不叠加 |
| 手机极小视口 | 双图太小难以触控 | 保持无滚动与正方形；简化标记密度，一键切单图编辑 |
| 香港网络高抖动 | 位置更新不稳定 | 全队各运营商 RTT / P95 实测，选路更优的节点；保留客户端重连 / 插值 |
| 多人同时修改 | 标记覆盖 / 丢失 | 操作 ID 去重、服务器定序与版本号、后写覆盖、操作广播、软删除和撤销；冲突提示留待下一轮视需要评估 |
| 战局识别错误 | 标绘或地图串到其他战局 | BATTLE-01：mission.json 状态转换 + 图像哈希 / 范围跨提供者匹配；不一致时网页人工确认，确认前不切换 |
| 本人状态判定不准 | 友军图标消失或误显示 | 显式状态上报，不静默；灰显最后已知位置 + 数据年龄；用 DATA-04 样本校准判定规则 |
| 未签名 Agent 被 SmartScreen / 杀软拦截 | 队员无法安装或启动 Agent，缺少位置与地图来源 | AGENT-02：一页带截图的安装说明；评估代码签名 |
| 自动敌情的合规风险 | 项目无法用于正式比赛 | 本期敌情只接受人工标绘，自动记录敌人单独研究并询问官方 |
| 域名 / DNS 到期或解析错误（次要） | 网页与 WSS 无法访问 | 开启域名自动续费；监控域名与证书到期；DNS 配置纳入部署文档。证书由 Caddy 自动续期 |

## 13. 最终执行建议

**先完成第一周竖切与 P0，再以 V10 UI 为固定设计基准进入联机开发。**早期版本不要继续增加战损面板、敌人受损分类和复杂“命令管理”功能；钢笔曲线等精细编辑工具放到首次实战测试之后。第一阶段真正必须做对的是：

1. 两个不同范围的地图能够精确叠加同一份世界坐标。
2. 所有参战队员的位置与朝向能够可靠及时地出现在网页。
3. 单图画的每个标点、方向和进攻路线能够立即同步到其他人的单双地图。
4. 地图始终正方形、全屏无滚动，手机上也能完成完整编辑流程。

这四件事完成并通过一场 8 人自定义对局验证，就得到真正可用的首个连队战术地图版本。其余需求放入下一轮独立评审。
